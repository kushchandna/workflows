# Claude Code Agent: Requirements

Date: 2026-11-01

## Purpose

An implementation of the agent interface (`docs/agents/requirements.md`) that
runs the `claude` CLI.

- Distribution `workflows-agent-claude-code`, import
  `workflows.agent_claude_code`, folder `packages/agents/claude-code/`.
- Depends on `workflows-agent` and nothing else at runtime.
- Exposes one class: `ClaudeCodeAgent`.

## The machine's setup is used as it is

The agent runs `claude` the way a person would on the deploying machine.
Whatever is set up there applies to every call:

- login or API key,
- user and project settings and hooks,
- CLAUDE.md files, including the one in the working folder,
- MCP servers and plugins.

The package never turns any of these off or adds to them. Preparing the
machine is the end product's job.

## Building an agent

`ClaudeCodeAgent(model, claude_path="claude")`

| Setting | Notes |
|---|---|
| **model** | Required. Passed as `--model` unchanged. Aliases such as `opus` work. |
| **claude_path** | Optional. The `claude` executable to run, looked up on `PATH` when it's a bare name. |

Every call runs with `--permission-mode bypassPermissions`. There's no
setting for the permission mode. A headless call has no one to approve
anything, so bypass is the mode that fits.

## Making a call

One call is one `claude` process. Calls share no state, so any number of them
can run at the same time.

### Command

```
claude -p
  --output-format stream-json --verbose
  --model <model>
  --permission-mode bypassPermissions
  [--add-dir <folder>]...                         one per extra folder
  [--append-system-prompt-file <temp file>]       only when a system prompt is given
```

- The process runs with the working folder as its current directory.
- The prompt is written to the process's stdin, and then stdin is closed. It
  isn't passed as an argument. Linux limits a single argument to 128 KB, and
  workflow prompts can carry large diffs.
- The system prompt goes through a temporary file for the same reason. The
  file is deleted when the call ends.
- The environment is inherited unchanged.
- Sessions are saved as normal, so a person can open one later with
  `claude --resume <session id>`.

### Reading the output

- stdout is read line by line until the process exits. Lines arrive after
  the `result` line too, so reading doesn't stop at it.
- A single line can be very large, for example a tool result holding a whole
  file. The reader must not fail on long lines. asyncio's default 64 KB line
  limit isn't enough.
- stderr is read at the same time and kept for errors, so neither pipe can
  fill up and block the process.

### Event mapping

Each stdout line becomes zero or more events. Every event carries the parsed
line (or, for a line that isn't JSON, the raw text) as `raw`.

| CLI line | Event |
|---|---|
| `assistant`, content block `text` | `TextEvent(text)` |
| `assistant`, content block `thinking` with non-empty text | `ReasoningEvent(text)`. Empty thinking blocks are dropped. |
| `assistant`, content block `tool_use` | `ToolCallEvent(tool_call_id=id, name, input)` |
| `user`, content block `tool_result` | `ToolResultEvent(tool_call_id=tool_use_id, output, is_error)`. If `content` is a list, the `output` is its text parts joined with newlines. `is_error` defaults to false. |
| `result` | `UsageEvent` with the totals (see Result), sent once |
| anything else (`system`, hooks, `rate_limit_event` and so on), or a line that isn't JSON | `OtherEvent` |

- One CLI line can hold several content blocks. Their events are emitted in
  block order.
- Usage isn't taken from `assistant` lines. The CLI repeats each message's
  usage on every block, so adding it up would count it twice.

### Result

Built from the `result` line:

| Field | Source |
|---|---|
| **call_id** | Generated by the agent (`uuid4().hex`), the same one the events carry. |
| **final_message** | `result` |
| **session_id** | `session_id` |
| **duration_seconds** | Wall-clock time of the call, measured by the agent. |
| **usage.input_tokens** | `usage.input_tokens + usage.cache_creation_input_tokens + usage.cache_read_input_tokens`. `input_tokens` alone leaves out cached input, which is most of it. |
| **usage.output_tokens** | `usage.output_tokens` |
| **usage.cost_usd** | `total_cost_usd` |

Any of these that's missing from the line is left empty.

## Errors

The call raises `AgentError` when any of these happen:

| Case | Message |
|---|---|
| `claude_path` can't be found or run | That the executable wasn't found, with the path. |
| The `result` line has `is_error: true` | The `result` text. The CLI reports some failures with `subtype: "success"` and `is_error: true`, so `is_error` decides, not `subtype`. |
| The process exits non-zero | The exit code. |
| The process exits with no `result` line | That the CLI ended without a result. |

- Every `AgentError` carries the collected stderr and, when one was seen, the
  session id.
- **Timeout:** the process is stopped (see below), and the call raises
  `AgentTimeoutError`.
- **Cancellation:** the process is stopped, and `CancelledError` is raised
  again.
- **`on_event` raises:** the process is stopped, and the same exception is
  raised again.

### Stopping the process

- `claude` starts child processes of its own, such as shells and MCP servers.
  It's started in a new process group so they can all be stopped together.
- Stopping sends SIGTERM to the group, waits 5 seconds, then sends SIGKILL to
  whatever is still running.
- The group is also stopped as soon as `claude` exits, so a leftover child
  can't keep its output open and make the call hang.
- **Known limit:** `claude` starts its Bash-tool shells and hook commands
  detached, in their own session (seen in CLI 2.1.314). Stopping the group
  doesn't reach them. Cleaning them up relies on `claude` handling SIGTERM.
  If `claude` has to be killed with SIGKILL, a running tool command can be
  left behind. This is accepted for now.

## Testing

- **Unit tests** (`packages/agents/claude-code/tests/`) don't run the real
  CLI. They point `claude_path` at a small fake `claude` script that:
  - checks the arguments and stdin it receives,
  - replays recorded stream-json fixtures,
  - exits with a chosen code.

  The fixtures are recorded from real CLI runs, including a run that fails
  with `is_error: true`.
- **Integration tests** live in the repo root's `tests/integration/` and run
  the real `claude` with a cheap model. They're skipped unless
  `WORKFLOWS_INTEGRATION=1` is set, because they need a logged-in CLI and
  cost money.

## Out of scope for the first version

- Choosing the permission mode.
- Passing any other CLI flags (tool lists, MCP config, settings files, budget
  or turn limits, fallback model).
- Turning off the machine's settings, hooks, MCP servers or plugins.
- Resuming sessions.
- Streaming partial messages (`--include-partial-messages`).
- Windows. Stopping a process group as described above is POSIX-only.

## Decisions

Decided by the user:

- Runs the `claude` CLI directly, not the Python Agent SDK.
- Uses the machine's Claude Code setup as it is (login, settings, CLAUDE.md,
  MCP servers, plugins).
- Every call runs in `bypassPermissions` mode. The permission mode isn't a
  setting.
- The only agent settings are model and where to find the CLI.
- Tool shells that `claude` starts detached aren't tracked. Their cleanup is
  left to `claude`'s own SIGTERM handling for now.

Claude's calls (overridable):

- `claude_path` setting, with a default of `claude` on `PATH`.
- The prompt goes through stdin and the system prompt through a temporary
  file, to avoid argument size limits.
- Sessions are kept, not run with `--no-session-persistence`, so a person
  can open them later.
- Empty thinking blocks are dropped, not sent as empty reasoning events.
- Usage is sent once, from the `result` line, not per message.
- Input tokens include cache creation and cache reads.
- `is_error` decides failure, not `subtype`.
- The process runs in its own process group, and stopping it means SIGTERM,
  then SIGKILL after 5 seconds.
- Unit tests use a fake `claude` script that replays recorded fixtures.
  Integration tests are gated by `WORKFLOWS_INTEGRATION=1`.
